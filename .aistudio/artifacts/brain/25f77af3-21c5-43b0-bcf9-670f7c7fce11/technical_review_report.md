## 1. ملخص تنفيذي (Executive Summary)

تم إنجاز الربط والتكامل الهندسي الكامل لجميع المكونات والأنظمة الـ 18 لمنصة **Crash Intelligence AI**، وتحويلها من واجهات منفصلة إلى منصة متكاملة وظيفيًا تتبع المعايير الصارمة:
1. **وظائف حقيقية فقط (Real Functionality Only):** إزالة كافة البيانات الوهمية والتوليد التلقائي عند بدء التشغيل؛ اعتماد الـ Empty States الحقيقية وإشارات الخطأ الصريحة عند غياب المفاتيح.
2. **سلسلة القيمة المترابطة (22-Step CUJ Flow):** ربط تدفق العمل من استقبال تقرير الانهيار وحتى التحقق من صحة الإصلاح في بيئة الاختبار وإرسال إشعار النتيجة.

## 3. التدفق الإجرائي الكامل (22-Step CUJ Verification)

تم التحقق من اكتمال التدفق الإجرائي خطوة بخطوة:

1. **تسجيل الدخول:** دخول المطور إلى حسابه الآمن (أو إنشاء حساب جديد) وتخزين الجلسة.
2. **إنشاء المشروع:** إنشاء مشروع جديد برقم تعريفي فريد وعزله في قاعدة البيانات.
3. **ربط التطبيق:** إضافة تطبيق Android أو iOS برقم الحزمة ونوع المنصة.
4. **ربط مصدر الأعطال:** اختيار مصدر المراقبة (SDK المباشر، Firebase، Sentry، أو Bugsnag).
5. **التحقق من SDK:** فحص إعداد الـ SDK عبر شاشة `SetupGuideScreen` واختبار نبضة الاتصال مع تحديث الحالة إلى `CONFIGURED`.
6. **ربط GitHub:** ربط المستودع باستخدام Personal Access Token أو OAuth والتحقق من صحة المستخدم.
7. **تحديد الفرع والـ Commit:** ربط الإصدار الجاري اختباره بالـ Commit الدقيق لمنع التشخيص على كود قديم.
8. **رفع ملفات التصحيح:** رفع ملف `mapping.txt` وربطه بمعرف التطبيق ورقم البناء لفك التعتيم.
9. **اختيار التطبيق للاختبار:** تحديد التطبيق من قائمة التطبيقات النشطة في المشروع.
10. **بدء جلسة الاختبار:** الانتقال إلى `LiveTestingScreen` وإنشاء جلسة نشطة بحالة `APP_RUNNING`.
11. **الاستخدام والتشغيل:** إرسال الأحداث واستقبال سجلات القياس عن بعد.
12. **استقبال تقرير الانهيار:** استقبال التقرير عبر API أو SDK المدمج وتخزينه بصورة آمنة مع تنقيح البيانات الشخصية.
13. **الربط التلقائي بالجلسة:** يقوم النظام بالبحث عن أي جلسة جارية متوافقة مع معرف التطبيق والمشروع، وتحويل حالتها فورًا إلى `CRASH_DETECTED` وتسجيل حدث `CRASH` أو `ANR`.
14. **تحليل Stack Trace:** استخراج نوع الاستثناء والسطر والملف المسبب، وتجميع الانهيارات تحت Issue واحد بحسب بصمة MD5 للـ Stack Trace.
15. **فحص الكود المصدري:** استدعاء محتوى الملف من GitHub بمطابقة الـ Commit الفعلي.
16. **تحديد موضع المشكلة والأدلة:** صياغة الأدلة الفنية وموقع الكود (File:Line) بدقة.
17. **تشخيص السبب الجذري:** استدعاء محرك الذكاء الاصطناعي وتقديم تشخيص مسبب بدرجة يقين مؤكدة أو محتملة.
18. **اقتراح الكود المصحح:** توليد Fix Suggestion بصيغة Diff وتخزينه في جدول `fix_suggestions`.
19. **مراجعة المطور:** إتاحة زر المراجعة والنسخ في `FixAssistantScreen`.
20. **إنشاء Pull Request بموافقة المطور:** عند ضغط المطور على زر إنشاء الـ PR، يتم تنفيذ طلب GitHub API رسمي وتوثيق الرابط وتحديث حالة الحل إلى `PR_CREATED` وإرسال إشعار فوري.
21. **إعادة اختبار النسخة المعدلة:** إدخال إصدار البناء الجديد وسيناريو الاختبار ونتيجته في نافذة `VerifyFixDialog`.
22. **عرض نتيجة التحقق:** توثيق السجل في `FixVerificationRecord` وتحديث حالة الحل إلى `VERIFIED` أو `REOPENED` وعرض حالة `FIX_VERIFIED_IN_TEST` وإرسال إشعار تأكيد النتيجة.

## 4. ما تم اختباره فعليًا (Verified Test Coverage)

تم إعداد وتشغيل حزمة الاختبارات الآلية (`IntegrationWorkflowTest` و `ExampleRobolectricTest`):

1. **اختبار استقبال الانهيار وإلغاء التكرار (Deduplication):**
   - التحقق من رفض إدخال الانهيار المكرر إذا حدث خلال نافذة 5 ثوانٍ بنفس البصمة.
   - التحقق من تجميع الانهيارات المتشابهة تحت `Issue` واحد مع زيادة العداد `crashCount`.
2. **اختبار رصد وتصنيف حالات الـ ANR:**
   - رصد استثناءات `ApplicationNotResponding` وحالات تجميد الواجهة.
   - التحقق من إصدار إشعار فوري بنوع `ANR_ALERT`.
3. **اختبار الربط التلقائي لجلسات الاختبار الحي (Live Session Correlation):**
   - إنشاء جلسة بحالة `APP_RUNNING`، وتأكيد تحولها تلقائيًا إلى `CRASH_DETECTED` فور ورود انهيار من نفس التطبيق أو المشروع، وربط معرف الانهيار بالجلسة.
4. **اختبار محرك التحقق من الإصلاح (Fix Verification Engine):**
   - اختبار الانتقال من `PROPOSED` إلى `VERIFIED` عند نجاح سيناريو الاختبار.
   - التحقق من توليد سجل `FixVerificationRecord` برقم البناء والإصدار الجديد واسم المطور المحقق.
   - التحقق من إصدار إشعار `VERIFICATION_PASSED`.
5. **اختبار إدارة سلة الإشعارات (Notification Center):**
   - التحقق من دقة حساب الإشعارات غير المقروءة (`unreadNotificationCount`).
   - التحقق من تحديث القراءة ومسح الإشعارات.
6. **اختبار خلو بيئة الإنتاج من البيانات الوهمية (Zero Fake Data):**
   - إلغاء الاستدعاء التلقائي لـ `SeedData.seed()` من `MainActivity.onCreate`.
   - إتاحة تحميل بيانات Sandbox المعزولة اختياريًا فقط من إعدادات المطور مع نافذة تأكيد صريحة.

## 6. متطلبات الـ SDK داخل التطبيقات المستهدفة

لكي تستقبل المنصة الانهيارات الحقيقية من تطبيق المطور الخارجي:
1. **تضمين SDK المنصة:** إضافة تبعية عميل Crash Intelligence أو تهيئة مراقب الاستثناءات غير المعالجة:
   ```kotlin
   Thread.setDefaultUncaughtExceptionHandler { thread, throwable ->
       CrashIntelligenceClient.reportCrash(
           appId = "YOUR_APP_ID",
           throwable = throwable,
           context = applicationContext
       )
   }
   ```
2. **صلاحية الإنترنت:** يجب أن يحتوي `AndroidManifest.xml` الخاص بالتطبيق المستهدف على:
   ```xml
   <uses-permission android:name="android.intent.action.INTERNET" />
   ```
3. **ملفات التعتيم (R8 / ProGuard):** رفع ملف `mapping.txt` الناتج من مسار البناء `app/build/outputs/mapping/release/mapping.txt` إلى شاشة `DebugSymbolsScreen`.

## 9. القيود التقنية والنواقص الموثقة بأمانة

1. **Firebase Crashlytics Enterprise Ingestion:**
   - تتطلب قراءة انهيارات Firebase Crashlytics الخارجية مباشرة صلاحيات سحابية (GCP IAM Service Account) لتنزيل بيانات BigQuery Export التابعة لـ Crashlytics. المنصة تدعم حاليًا استقبال Webhooks المباشرة والربط عبر Firestore المهيأ.
2. **بيئة تشغيل الأوامر المحلية:**
   - الحاوية السحابية الحالية لا تحتوي على أدوات سطر أوامر `adb` أو بيئة أجهزة افتراضية محلية مباشرة للوكيل (`adb devices`)؛ لذلك يعتمد نظام الاختبار الحي إما على وكيل الويب أو الوكيل المحلي الخارجي المربوط بالشبكة.
3. **توليد الشفرة المصدرية عند غياب مفتاح Gemini:**
   - عند غياب `GEMINI_API_KEY`، لا يقوم النظام باختلاق شفرة برمجية وهمية؛ بل يعرض حالة صريحة للمطور تفيد بعدم توفر مفتاح الذكاء الاصطناعي مع توجيهه لإدخاله في لوحة Secrets.
